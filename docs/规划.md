# FlagTensor 验收导向重构规划

本规划以《算子库验收规范》为验收主线，对照参考仓库 FlagGems 与当前 `flagtensor` 现状，提出一套在保持现有功能可用前提下、分阶段推进到可验收状态的仓库重构路线。

## 1. 目标与约束

- **目标**
  - 让 `flagtensor` 在仓库结构、测试入口、CI/CD、文档与验收产物上满足验收规范。
  - 保持现有算子实现、benchmark 能力、weekly/CI runner 能力不被破坏。
  - 尽量向 FlagGems 的工程组织方式靠拢，降低后续维护与验收成本。

- **约束**
  - 不做“推倒重来”式改造，优先采用兼容迁移。
  - 短期先满足验收所需的“可检查、可执行、可追踪”，中期再做深层架构统一。
  - 所有迁移必须保证现有 `src/flagtensor/ops`、`ctests`、`benchmark`、`tools` 的功能可回归验证。

## 2. 当前现状摘要

### 2.1 已具备的基础

- 已有独立 Python 包：`src/flagtensor`
- 已有算子实现目录：`src/flagtensor/ops`
- 已有运行时/工具基础：`runtime`、`utils`、`benchmark_core.py`、`visualization.py`
- 已有 correctness/perf/weekly runner：
  - `tools/run_flagtensor_ci.py`
  - `tools/run_flagtensor_weekly.py`
- 已有 GitHub Actions workflow：
  - `.github/workflows/ci.yaml`
  - `.github/workflows/weekly.yaml`
- 已有一批 correctness/perf 用例与 benchmark 结果导出能力

### 2.2 与验收规范/FlagGems 的主要偏差

1. **项目结构尚未对齐规范**
   - 验收规范要求：`tests/` 作为统一精度测试目录，且按类别组织。
   - 当前 `flagtensor` 使用的是 `ctests/`，且基本是一算子一文件，未形成按类别聚合。
   - `benchmark/` 目前也是一算子一性能文件，未形成类似 FlagGems 的按类别测试组织。
   - 缺少规范中明确提及的 `include/`、`lib/` 的明确定位说明；`docs/` 基本为空。

2. **缺少算子接口注册表**
   - 验收规范明确要求“算子接口注册表”作为测试/检查入口。
   - 当前 `flagtensor` 主要依赖目录扫描和 `weekly_op_test.txt`，缺少统一、可 diff 的权威注册表。

3. **测试规范未沉淀为统一机制**
   - 目前 correctness/perf 能跑，但：
     - 缺少类似 FlagGems `tests/accuracy_utils.py` 的统一精度断言/容差/shape 管理中心。
     - FlagTensor 领域库专属的“精度原则、容差标准、测试 shape 原则”仍处于文档 TODO 状态。
   - mark 基本依赖算子名，但缺少由注册表驱动的统一校验机制。

4. **性能测试框架与验收口径存在偏差**
   - 当前 benchmark 框架可用，但与 FlagGems 的“按类别测试 + 日志解析 + 聚合统计”组织方式不同。
   - `kernel/operator/wrapper` 模式是当前特色能力，但尚未完全纳入统一验收口径说明。
   - 报告生成与 runner 对 benchmark mode 的识别仍有统一性缺口。

5. **工程质量门禁不足**
   - 当前仓库没有看到 `.pre-commit-config.yaml`。
   - `pyproject.toml` 中尚未体现 lint/format/test 的统一配置。
   - 日志规范要求使用 `logging`，但当前 runner/脚本仍明显偏 `print` 风格。

6. **CI/CD 仍处于“可跑”而非“可验收”状态**
   - 当前 CI/weekly workflow 已成型，但与验收规范中的“工程质量 / 正确性 / 兼容性 / 发布”全链路一致性仍有差距。
   - 缺少明确的静态检查 job、发布构建验证、注册表一致性检查、测试覆盖检查。

7. **仓库内存在较多临时性结果目录与本地产物心智负担**
   - 如 `ci_results_*`、`weekly_results_*`、HTML 报告等容易与源码混杂。
   - 验收视角下需要更明确地区分“源码/规范文件/自动产物/临时结果”。

## 3. 目标架构（建议）

在不立即破坏现有目录的前提下，建议向下述结构演进：

```text
flagtensor/
├── src/flagtensor/
│   ├── ops/
│   ├── fused/              # 若暂时为空，可先预留
│   ├── modules/            # 若暂时为空，可先预留
│   ├── runtime/
│   ├── utils/
│   └── testing/
├── tests/
│   ├── unary/
│   ├── binary/
│   ├── contraction/
│   ├── sparse/
│   ├── accuracy_utils.py
│   └── conftest.py
├── benchmark/
│   ├── attri_util.py / shapes.py
│   ├── performance_utils.py
│   ├── core_shapes.yaml
│   ├── test_unary_perf.py
│   ├── test_binary_perf.py
│   ├── test_contraction_perf.py
│   └── ...
├── conf/
│   └── operators.yaml
├── tools/
├── docs/
│   ├── acceptance/
│   ├── testing_strategy.md
│   └── benchmark_strategy.md
├── .github/workflows/
├── .pre-commit-config.yaml
├── pyproject.toml
└── README.md
```

### 关键原则

- **短期保留 `ctests/`**，但新增 `tests/` 并逐步迁移。
- **短期保留一算子一 benchmark 文件**，但新增“类别聚合 benchmark 文件”作为验收入口。
- **用注册表 `conf/operators.yaml` 驱动测试、weekly、验收和报告**。
- **把领域特有的 `kernel/operator/wrapper` 模式写成显式规范**，避免与 FlagGems 只做表面一致。

## 4. 分阶段重构路线

## 阶段 A：先补齐验收最小闭环（1~2 周，优先级最高）

### A1. 建立算子接口注册表

- 新增 `conf/operators.yaml`
- 字段至少包含：
  - `name`
  - `category`
  - `python_api`
  - `impl_file`
  - `correctness_mark`
  - `benchmark_mark`
  - `benchmark_modes`
  - `status`（stable/experimental/blocked）
  - `skip_reason`（可选）
- 用该注册表替代：
  - 手写 `weekly_op_test.txt`
  - 目录扫描作为唯一来源的策略
- 增加一致性检查：
  - 注册表中的算子必须能映射到实现/测试/benchmark
  - 测试 mark 必须与注册表一致

### A2. 补齐工程质量基础设施

- 新增 `.pre-commit-config.yaml`，优先复用 FlagGems 版本并按 `flagtensor` 依赖微调。
- 在 `pyproject.toml` 中增加统一工具配置（black/isort/flake8/pytest 入口）。
- 增加基础文档：
  - 如何安装 pre-commit
  - 如何运行 correctness/perf/weekly
  - 如何更新 operator registry

### A3. 明确 FlagTensor 自身测试规范

把《算子库验收规范》中 FlagTensor 仍是 TODO 的部分落地为项目文档：

- `docs/testing_strategy.md`
  - 精度参考实现原则（cuTensor baseline / CPU reference / 特殊算子例外）
  - 容差管理策略
  - 测试 shape 管理策略
- `docs/benchmark_strategy.md`
  - benchmark 指标定义
  - warmup / repetition / median 规范
  - `kernel/operator/wrapper` 三种 mode 的定义与适用范围
  - smoke 与 full 的区别

### A4. 验收 runner 改为注册表驱动

- `run_flagtensor_ci.py`
- `run_flagtensor_weekly.py`

都应支持：
- 从 `conf/operators.yaml` 选取算子
- 通过 category / status / mode 过滤
- 自动生成验收所需 summary

> 这一阶段结束时，仓库应达到“有统一入口、有统一清单、有可审计执行结果”的最低验收门槛。

## 阶段 B：结构对齐 FlagGems，但保持兼容（2~4 周）

### B1. 构建 `tests/` 正式目录并迁移 correctness

- 新增 `tests/` 目录，按类别组织：
  - `tests/unary/`
  - `tests/binary/`
  - `tests/contraction/`
  - `tests/sparse/`
- 新增：
  - `tests/accuracy_utils.py`
  - `tests/conftest.py`
- 将 `ctests/` 中现有用例逐步迁移到 `tests/`
- 迁移策略：
  - 第一阶段保留 `ctests/`，新老双入口共存
  - 第二阶段 runner 默认改跑 `tests/`
  - 第三阶段再下线 `ctests/`

### B2. 重组 benchmark 目录

从“每算子一个文件”为主，演进到“按类别聚合文件为主”：

- 保留现有单算子 perf 文件，作为兼容层
- 新增类别 benchmark 文件：
  - `test_unary_perf.py`
  - `test_binary_perf.py`
  - `test_contraction_perf.py`
  - `test_sparse_perf.py`
- 提炼公共性能工具：
  - `benchmark/performance_utils.py`
  - `benchmark/core_shapes.yaml`
  - 统一 shape/dtype/mode 配置

### B3. 建立 `src/flagtensor/testing/`

把当前零散的测试辅助逻辑沉淀到正式包内：

- 统一断言 API
- 统一 dtype 容差表
- 统一 reference 转换逻辑
- 统一 shape 采样策略
- 统一 skip/xfail 理由模板

### B4. 清理仓库边界

- 明确哪些目录属于：
  - 源码
  - 文档
  - benchmark 结果
  - CI/weekly 结果
  - 临时报告
- 用 `.gitignore` + README + docs 约束产物位置
- 避免验收时出现“结果文件混在仓库根目录”的观感问题

## 阶段 C：CI/CD 达到验收口径（2~3 周）

### C1. 增加静态质量 workflow

新增独立 job：
- pre-commit
- package install/build check
- registry consistency check

### C2. 完善 correctness workflow

- 从注册表驱动执行
- 输出：
  - summary.json
  - summary.md / xlsx
  - failed list
  - skip reason 汇总
- 明确区分：
  - smoke correctness
  - acceptance correctness

### C3. 完善 perf workflow

- 明确区分：
  - smoke perf
  - acceptance perf
  - weekly perf
- 统一报告口径：
  - 按 mode 读取 benchmark CSV
  - 区分 kernel / operator / wrapper
  - 支持两级平均统计

### C4. 构建发布检查与版本化产物

即使暂时不正式发布，也建议补齐：
- wheel/sdist build check
- 版本号规范
- changelog / release note 模板

## 阶段 D：完成正式验收资产建设（1~2 周）

### D1. 形成“验收包”

建议在 `docs/acceptance/` 下生成固定资产：

- `acceptance_checklist.md`
- `operator_coverage.md`
- `accuracy_policy.md`
- `benchmark_policy.md`
- `ci_matrix.md`
- `known_issues.md`

### D2. 形成固定验收命令

对外统一成 3~5 条标准命令：
- 安装与 pre-commit
- correctness 全量
- perf 全量
- weekly 验收
- HTML / XLSX 报告生成

### D3. 形成“已达标/未达标”矩阵

按验收规范逐条打状态：
- 已满足
- 部分满足
- 未满足
- 风险项

## 5. 重点差距与建议动作清单

### 高优先级（必须先做）

- **算子注册表 `conf/operators.yaml`**
- **pre-commit 与基础 lint/format 机制**
- **FlagTensor 专属测试/benchmark 规范文档补齐**
- **runner 改为注册表驱动**
- **将 `ctests` 迁移到 `tests` 的兼容方案**

### 中优先级（验收前建议完成）

- **benchmark 按类别聚合重组**
- **统一测试辅助模块 `src/flagtensor/testing/`**
- **mode-aware 报告与统计体系**
- **CI 拆分为质量 / 正确性 / 性能 / weekly / 构建检查**

### 低优先级（可验收后继续优化）

- `fused/`、`modules/` 目录的实体化
- 发布自动化
- 更细粒度 tolerance / shape 策略自动生成
- 更丰富的可视化报告

## 6. 建议的实施顺序

1. **先补注册表 + 文档规范 + pre-commit**
2. **再改 runner 与 workflow 入口**
3. **再迁 correctness 到 `tests/`**
4. **再迁 benchmark 到按类别组织**
5. **最后整理验收资产与正式报告**

这样可以保证：
- 每一步都可回归
- 不会先做大规模目录迁移导致现有流程失效
- 验收方能尽早看到“规范化成果”

## 7. 对当前仓库的直接判断

如果按当前状态直接验收，**大概率无法一次通过**，主要卡点会在：

- 缺少统一算子注册表
- `tests/` 结构未对齐规范
- FlagTensor 自身精度/性能规范仍未正式定稿
- pre-commit / 静态检查机制缺失
- CI/CD 还未完全达到 FlagGems 同口径
- 报告与测试入口存在 mode/结构层面的统一性不足

但从工程基础上看，`flagtensor` **已经具备较好的“可重构到达标”条件**：
- 包结构已建立
- 算子/测试/benchmark/runner 已具备雏形
- workflow 已存在
- 主要问题是“统一化、规范化、注册化、验收资产化”还没完成

## 8. 我建议你下一步立刻启动的里程碑

### 里程碑 1：验收最小闭环
- 新增 `conf/operators.yaml`
- 新增 `.pre-commit-config.yaml`
- 补齐 FlagTensor 的测试/benchmark 规范文档
- runner 改为从注册表取算子

### 里程碑 2：结构迁移兼容层
- 建 `tests/`，保留 `ctests/`
- 建类别 benchmark 文件，保留单算子 perf 文件
- 建 `src/flagtensor/testing/`

### 里程碑 3：正式验收资产
- CI jobs 完整化
- acceptance checklist
- 标准验收命令
- 汇总报告模板固定化
